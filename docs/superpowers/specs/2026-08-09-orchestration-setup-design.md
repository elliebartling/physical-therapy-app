## Decisions taken

1. **Merge flow:** GitHub PR flow with CI, mirroring read-later.
2. **Xcode project file:** gitignore it, regenerate via `make gen`. `project.pbxproj` is the worst merge-conflict file in an Xcode repo and this removes the entire class.
3. **Scope:** full parity in one pass. A protocol whose substrate is half-missing is worse than none — a session that can't run `make test` improvises, which is precisely what the protocol exists to prevent.
4. **Repo is public** (owner's decision, 2026-08-29). This has consequences the original cost reasoning got backwards; see §4.

## 1. `AGENTS.md` — canonical agent briefing

New file at repo root. `CLAUDE.md` becomes a symlink to it (one file, two names, no drift).

### Sections

**Stack (pinned — do not upgrade without being asked)**
iOS 26.0 deployment target; SwiftUI + SwiftData; XCTest (**not** Swift Testing); ViewInspector for UI tests; project generated by XcodeGen.

Record the versions rather than a vague "Swift 6": the app target sets `SWIFT_VERSION: 6.0` in `App/project.yml`, while `Packages/PTAppCore/Package.swift` declares `swift-tools-version: 6.2`. These are different knobs and both are load-bearing. Verified toolchain on this machine: Xcode 26.6 (17F113), XcodeGen 2.45.4.

**Project file rule (most important)**
`App/PTApp.xcodeproj` is a gitignored build artifact. Never edit or commit it. **But route changes to the correct source of truth** — revision 1 sent everything to `project.yml`, which is wrong for two thirds of the codebase:

- App target, app build settings, Info.plist, schemes → `App/project.yml`, then `make gen`.
- The five libraries, the five test targets, and package dependencies → `Packages/PTAppCore/Package.swift`.

**Commands** — the make targets from §3.

**Architecture map**
A thin app shell (`App/PTApp/PTAppApp.swift`, `RootView.swift`) over the `PTAppCore` SPM package, which holds five libraries:

- `DataKit` — SwiftData models (`Routine`, `Exercise`, `ExerciseTarget`, `SessionRecord`, `Asset`) and repositories. The dependency root; depends on nothing.
- `ParsingKit` — Vision OCR + routine extraction. Depends on `DataKit`.
- `SessionKit` — `SessionEngine`, clock, audio cues, haptics. Depends on `DataKit`.
- `HistoryKit` — streak and heatmap computation. Depends on `DataKit`.
- `UI` — all SwiftUI surfaces and view models. Depends on all four.

`SessionKit` also ships bundled audio cues via `resources: [.process("Resources")]`.

Five test targets mirror this: `DataKitTests`, `ParsingKitTests` (with `Fixtures` resources), `SessionKitTests`, `HistoryKitTests`, `UITests` (ViewInspector).

### Invariants — split by whether they are true *today*

Revision 1 listed these as invariants "true before and after" the in-flight refactor. Verified against the code on 2026-08-29, most were not true at all. An agent told that a false statement is an invariant will write code to preserve a property that does not exist, or trust a guarantee the code never made. Splitting the list is the fix.

**True today — enforce these now:**

- `ParsingKit` must not import SwiftUI. (Note it *does* import UIKit, in `RoutineParser.swift`, for its `UIImage` entry point. That is allowed; SwiftUI is not.)
- Swift strict concurrency: every type crossing an async boundary must be `Sendable`.
- No new package dependencies without being asked.
- XCTest only — do not introduce Swift Testing alongside the existing suite.
- `ParsedRoutine.toRoutine()` coerces an unrecognized side to `.both`, via `Side(rawValue: p.side.lowercased()) ?? .both`. **It does not produce `nil`.** A malformed side is therefore silent, not detectable downstream — if the parsing work wants bad input to be visible, that coercion is the line to change.

**Target state — the in-flight parsing work must establish these; do not assert them as current:**

- `import FoundationModels` should appear in exactly one file in `ParsingKit`, quarantining the framework behind a `@Generable` DTO. *Today it appears in zero files* — `FoundationModelsParser.extract` is a stub that throws `NSError`.
- Extractor failures should fall through to the next extractor, with only OCR failure reaching the UI. *Today `RoutineParser` holds a single extractor and rethrows its error directly*, so any extractor failure surfaces in the UI.
- Heuristic parser defaults must match the LLM prompt. *Today the prompt defaults only `restSec` 30 and `side` "both"* — it does not mention sets 3 or reps 10. Whoever writes `HeuristicExtractor` must make the prompt and the heuristic agree, in whichever direction, and that is a change to both.

**Prohibited patterns**

- No `ObservableObject` / `@StateObject` in new code — use `@Observable`.
- No `NavigationView` — use `NavigationStack` / `NavigationSplitView`.
- No force-unwraps (`!`) **in new code**. Existing ones are grandfathered and listed here so nobody "fixes" them mid-feature and blows up the diff: `App/PTApp/PTAppApp.swift:12` (`try!` on the model container) and `Packages/PTAppCore/Sources/HistoryKit/HeatmapMatrix.swift:23-24`. Retiring them is its own task.
- No completion handlers where `async/await` works; no new GCD.
- No APIs above iOS 26 without `#available` gating.

## 2. Multi-session orchestration protocol

Goes in `AGENTS.md`, adapted from `orchestrating-parallel-sessions/protocol-template.md` and read-later's version.

Ellen runs several Claude/Cursor sessions on this repo in parallel. One dedicated session acts as the **Orchestrator** — it sequences merges, assigns file ownership, and tracks every branch in flight. Working sessions follow:

1. **Check merge order before starting or rebasing.** Cross-cutting changes (`App/project.yml`, `Packages/PTAppCore/Package.swift`, `Makefile`, CI, deployment target) land before feature branches; everything else rebases after them. If unsure whether an in-flight branch gates yours, ask before building on stale `main`.
2. **UI-touching PRs embed their screenshots — synthetic data only.** The repo is public and its history is permanent. A screenshot of a real PT handout puts a real person's medical instructions on the open internet, and deleting the file later does not remove the blob. **Never screenshot real handouts, real names, or real notification text.** Use fixture data. Reference images by immutable commit SHA URL, not branch URL, since branch URLs break when the branch is deleted.
3. **Report back at milestones** — PR opened, CI green, merge conflict, blocked, or finished. See the control plane below for where reports actually go.
4. **Declare file ownership early.** Hot files, with paths that actually resolve:
   - `App/project.yml`
   - `Packages/PTAppCore/Package.swift`
   - `App/PTApp/RootView.swift`
   - `Packages/PTAppCore/Sources/UI/DesignSystem/`
   - `Packages/PTAppCore/Sources/SessionKit/SessionEngine.swift`
   - `Packages/PTAppCore/Sources/ParsingKit/ParsedRoutine.swift` — the contract between `ParsingKit` and `UI`; a change to its shape breaks both sides even though the file is small.
   - `AGENTS.md`, `Makefile`
5. **Two contended resources, one at a time each.**
   - **The simulator.** Concurrent sessions stomp each other's installs.
   - **The physical Apple Intelligence device.** Foundation Models verification needs real hardware and, unlike the simulator, it cannot be duplicated. Claim it explicitly and release it explicitly.
6. **Stay in your own worktree.** Never edit the main checkout or another session's worktree unless the orchestrator hands that work to you.
7. **Don't merge your own PR** unless Ellen or the orchestrator says to.

### What actually enforces this (and what doesn't)

Revision 1 described rules with no mechanism behind them, which is how a protocol becomes decorative. Being honest about the split:

**Enforced by machine** — must be configured in §4, or it does not exist:
- No direct pushes to `main`; PRs required.
- CI status check required to merge.
- Rule 7 is real only once self-merge is blocked by a ruleset.

**Enforced by convention only** — depends on agents reading `AGENTS.md` and complying:
- Merge ordering, file ownership, resource claims, milestone reporting.

**Not enforced at all, and needs a decision:** there is no shared registry of who owns what, no lock or lease on the simulator and device, no claim expiry when a session dies mid-claim, and no channel that delivers a "Status for orchestrator" block to the orchestrator session. A status block printed into Ellen's terminal is not delivered anywhere. Until a control plane exists, resource claims are advisory and a crashed session holds its claim forever.

The minimum viable control plane is a single tracked file — `.claude/orchestration-board.md` — holding the branch registry and two claim lines with a timestamp and session name. It is racy, and that is acceptable at two or three sessions in a way it stops being at six. Revision 1 put the status board out of scope; that was wrong for a design whose entire purpose is several sessions, so it moves in scope here as the cheapest possible version.

### Sub-agent model policy

Implementation and code-review agents should run Opus; research agents may run Sonnet or better; trivial lookups anything. Stated as a preference, not a guarantee: `AGENTS.md` cannot force a model on a client that doesn't support the key, and an unsupported value may be silently ignored — the exact failure the rule is trying to prevent. Ellen should confirm the model in-session for work that matters rather than trusting the file.

### Worktree convention

Session worktrees live at `.claude/worktrees/<branch-name>`, gitignored. Unlanded diffs get backed up to `.claude/backups/` before any worktree is pruned.

## 3. `Makefile`

Adapted from read-later's, so every session and CI run the identical commands.

```make
SHELL := /bin/bash
.SHELLFLAGS := -eo pipefail -c
.PHONY: bootstrap gen open build test lint format clean
```

The `pipefail` guard is not cosmetic: without it, `xcodebuild ... | tail` reports the exit status of `tail` only, so a broken build exits 0. The `.PHONY` line is not cosmetic either — without it, a file or directory named `test`, `build`, or `gen` makes Make silently skip the recipe.

Variables: `SCHEME ?= PTApp`, `DESTINATION ?= platform=iOS Simulator,name=iPhone 17 Pro`. `SCHEME` applies to `build` and `open` only; `test` does not use it (see below).

Targets: `bootstrap` (verify `xcodegen` present, warn if `swiftformat` absent), `gen`, `open`, `build`, `test`, `lint`, `format`, `clean`. `gen` depends on `bootstrap`; `build`, `test`, and `open` each depend on `gen`, so a stale or missing project file can never reach a build.

**XcodeGen invocation:** the spec is at `App/project.yml`, not the repo root, so `gen` runs `xcodegen generate --spec App/project.yml --project App`. This differs from read-later, where the spec sits at the root.

### The `make test` question — resolved empirically 2026-08-29

Revision 1 flagged this as the document's most important unknown and required the implementation plan to verify it. It has now been verified by running every candidate. **The answer invalidates the invocation currently written into the in-flight plan doc.**

What was actually run, and what happened:

| Invocation | Result |
|---|---|
| `xcodebuild test -project App/PTApp.xcodeproj -scheme ParsingKit` | **`error: Scheme ParsingKit is not currently configured for the test action`** |
| `xcodebuild test -project App/PTApp.xcodeproj -scheme PTApp` | **same error** |
| `xcodebuild test -scheme PTAppCore-Package` (cwd `Packages/PTAppCore`) | **`** TEST SUCCEEDED **`, all five bundles** |

Two corrections follow:

**Revision 1's mechanism was wrong.** It said XcodeGen auto-generates one scheme per target when there is no `schemes:` block. XcodeGen does not: `App/project.yml` declares exactly one target (`PTApp`), the ten package targets are SwiftPM targets and invisible to it, and the generated project contains **zero** `.xcscheme` files. The `DataKit`/`ParsingKit`/`UI`/... schemes that appear in `xcodebuild -list` are Xcode's implicit package schemes, not XcodeGen's output — and none of them carry a test action.

**The plan doc is broken.** `docs/superpowers/plans/2026-08-09-finish-v1-parsing.md` instructs the implementer to run `xcodebuild test -project App/PTApp.xcodeproj -scheme ParsingKit -only-testing:ParsingKitTests`. That errors before running anything. Task 1 fails on its first step. Fixing this is a prerequisite of that plan, not an optional cleanup.

So `make test` runs the package's aggregate scheme:

```make
test: gen
	cd Packages/PTAppCore && xcodebuild test \
	  -scheme PTAppCore-Package \
	  -destination '$(DESTINATION)' \
	  CODE_SIGNING_ALLOWED=NO
```

**Verification must assert bundle coverage, not a test count.** A green run with four of five bundles silently dropped looks identical to a correct one. The measured baseline on 2026-08-29 was five bundles — `DataKitTests` 8, `HistoryKitTests` 8, `SessionKitTests` 7, `ParsingKitTests` 5, `UITests` 5 (33 total) — but the count is the wrong thing to pin, because the parsing work will change it by design. Pin the **set of bundle names**: the implementation plan should add a check that all five `*Tests.xctest` bundles appear in the run, and fail if any is missing.

`make build` must also be exercised. The package suites can pass while the app target is broken, since they never compile it.

### swiftformat

Not installed on this machine (confirmed) and the repo has no swiftformat config. Do **not** copy read-later's `swiftformat --lint . || true` — that converts a genuine lint failure into a pass.

But "skip cleanly when absent" has the same defect in a milder form: it makes "clean" and "tool missing" indistinguishable to automation, and on this machine `lint` would *always* be a passing no-op. So: `lint` exits non-zero with an install hint when swiftformat is absent, and CI does not depend on `lint` until the tool and a pinned config are actually committed. A target that cannot fail is not a check.

- `main` (209de1b) pushed and **set as the default branch** via `gh api -X PATCH ... -f default_branch=main`, so PRs target it.

- The Mend commit is preserved on `claude/physical-therapy-app-g95iac` as a reference branch — it carries watchOS, HealthKit, and TestFlight-CI work worth mining later, and none of it has ever compiled.
- The repo is **public**, by decision. It was secret-scanned before the first push.

Success criterion 4 in revision 1 ("a PR against the new repo") was unsatisfiable as written. It is restated below.

### Branch protection — the missing gate

Revision 1 called CI a "merge gate" and told agents not to self-merge, then specified only a workflow file. **A workflow is not a gate.** With no ruleset, every rule in §2 that matters is voluntary, and any session can push straight to `main`.

Public repos on GitHub Free can enforce rulesets. Configure on `main`:

- Require a pull request before merging.
- Require the CI status check to pass.
- Block force-pushes and deletion.

This is what makes protocol rule 7 real. Without it, §2's merge sequencing is a suggestion.

### `.github/workflows/ci.yml`

- **Triggers:** `pull_request` plus `push` to `main` only. Not `push: ["**"]` — that pair runs every PR-branch push twice under two concurrency groups where neither cancels the other.
- **Cost reasoning corrected.** Revision 1 justified trigger filtering by 10× macOS billing on private repos. The repo is public, where GitHub-hosted runners are free. Concurrency cancellation and `timeout-minutes` stay — they buy latency and queue capacity, not money — but nobody should defend these choices on cost grounds now.
- **`paths-ignore` must not be applied to a required check.** A workflow skipped by path filtering never reports, so a required check stays Pending forever and a doc-only PR can never merge. Since the CI check *is* becoming required, the job must always run and decide internally: a cheap always-reporting gate job, with the expensive macOS job conditioned on changed paths.
- **Concurrency group** with `cancel-in-progress: true`.
- **`timeout-minutes: 20`.**
- **`defaults.run.shell: bash`** — explicit bash runs with `-eo pipefail`; the implicit default shell does not.
- **Pin the environment.** "Local and CI cannot drift" is only true if both are pinned. Specify the `runs-on` image explicitly, select Xcode explicitly (the project needs 26.x; local is 26.6), and pin the XcodeGen version rather than `brew install xcodegen`, which installs whatever is current that day.
- **Public-repo fork behavior.** Fork PRs run with restricted tokens and no secrets. Set explicit minimal `permissions:` on the workflow.
- **Simulator selection.** Choosing a simulator dynamically accomplishes nothing unless the chosen destination is passed into the same `make test` invocation — export it via `$GITHUB_ENV` and have `make test` consume `DESTINATION`.
- **Steps:** checkout → pin Xcode → install pinned XcodeGen → `make gen` → `make build` → `make test`, with `CODE_SIGNING_ALLOWED=NO`.

### Ordering procedure for the untracking step

`git rm --cached` keeps the file on disk only where it runs. The commit records a deletion, so any in-flight branch that checks out or rebases onto the new base can have its project file removed, or hit a delete/modify conflict if it edited `project.pbxproj`. Revision 1 said only "cross-cutting work lands first," which is not a procedure. Before the migration:

1. Inventory every branch, worktree, and running session — including remote branches and the peer sessions listed by the session tooling. Local ref equality is not evidence of quiet (see §Why now).
2. For any branch that touched `App/PTApp.xcodeproj`, transfer the semantic change into `App/project.yml` and discard the generated-file edit. Do not attempt to merge `project.pbxproj`.
3. Prove regeneration before deleting the only proven project: run `make gen && make build && make test` and confirm all five bundles. *Encouraging data point from 2026-08-29: regenerating over the committed project produced a byte-identical tree (`git status` clean), so the committed file and XcodeGen's output currently agree.*
4. Land the migration, then have each in-flight branch rebase and re-run `make gen`.

## Success criteria

1. A fresh clone can run `make gen && make build && make test` and get a real result — **all five test bundles present**, not merely a non-zero count.
2. `App/PTApp.xcodeproj` no longer appears in `git ls-files`.
3. `AGENTS.md` and `CLAUDE.md` both resolve to the same content.
4. A PR into `main` triggers CI; CI **fails** when a test fails, verified with a deliberately broken commit. A green-only check proves nothing.
5. A ruleset on `main` blocks direct pushes and blocks merging with a failing check — verified by attempting both.
6. A doc-only PR reaches a mergeable state rather than hanging on a skipped required check.
7. `finish-v1-parsing` sits cleanly on top of the new `main`, with its plan doc's test commands corrected.
